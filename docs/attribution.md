# 越限归因与敏感性分析（I4）

> 从"超了"升级到"**哪里超、什么时候超、为什么超、动谁最有效**"。
> 所有数字可由 `uv run python scripts/verify_analysis.py` 复现。

---

## 1. 四块能力

| 函数 | 回答的问题 | 对应排期 |
|---|---|---|
| `build_attribution()` | 哪些设备、在哪些时段、超了多少、持续多久 | 4.1 / 4.2 |

## 2. 归因报告（4.1）

把"越限"拆成**事件列表**：每台设备、每条约束的每一段**连续**越限区间。

```
ViolationEvent:
    constraint, element_type, element_index
    start_step, end_step, start_time, end_time
    n_steps          真实越限时段数
    duration_steps   区间跨越的时段数（合并空档时 > n_steps）
    peak_step, peak_time, peak_value
    peak_excess      峰值越限量（p.u. 或 %）
    peak_severity    peak_excess / limit
    mean_severity    区间内平均相对幅度
```

**首次越限**（`first_violation`）按时间取第一条，不是按幅度。这与排期 DoD 的
"首次越限时刻"一致；同时也给出 `top_by_peak_severity` 供"最严重的是哪个"使用。

### merge_gap：为什么要合并空档

真实越限会因云遮挡、负荷小波动在时间上碎裂。实测 bus17 接 4 MW：

| merge_gap | 事件数 | bus16 的事件 |
|---|---|---|
| 0 | 4 | `[44,58]` 与 `[60,60]` 两段 |
| ≥4 | 3 | `[44,60]` 一段（17 个真实越限 + 3 个空档） |

默认 `merge_gap=0`（不合并，最大信息量），由调用方按展示需要显式合并。
合并后 `n_steps`（真实越限 17）与 `duration_steps`（区间跨度 20）不同，两者都返回。

### 实测例子

bus17 接 4.0 MW（I3 承载力 3.069 MW），SimBench 光伏最大日，GB/T 约束：

```
首次越限：10:45，voltage_high，bus 17
持续时间：19 个时段（4 h 45 min）
峰值：     13:30，1.0992 p.u.（限值 1.07，相对幅度 2.74%）
事件总数： 4（涉及 3 个节点：17 / 16 / 15）
```

## 3. 热力图（4.2）

`bus × time` 的**归一化裕度矩阵**，越限处为负的偏离量。

```
电压： margin = min( (vm - vm_min)/vm_min , (vm_max - vm)/vm_max )
线路： margin = (limit - loading) / limit
```

取"离最近那条限界"的距离，所以**下限越限与上限越限会落在同一个符号体系里**：
负值即越限，越负越严重。值域截断到 `[-1, 0]`（越限部分），避免极端值压扁色阶。

输出结构直接对应 ECharts `heatmap`：

```json
{
  "elements": [0, 1, ...],        // y 轴（节点编号）
  "step_times": ["00:00", ...],   // x 轴（96 个时刻标签）
  "data": [[52, 17, -0.027], ...],  // [x=step, y=elementPos, value]
  "value_range": [-1, 0]
}
```

**只输出越限单元**。有余量的格子对"哪里出了问题"没有信息量，全量输出 96×33
只会让响应体变大、前端渲染变慢。实测 40 个格子（4 MW 场景）。

演示页：`docs/figures/heatmap_demo.html`（数据内嵌，双击可看，`export_heatmap_demo.py` 生成）。

## 4. 灵敏度（4.3）

中心差分：

$$
\frac{\partial f}{\partial P}\Big|_{P_0} = \frac{f(P_0 + \Delta P) - f(P_0 - \Delta P)}{2\,\Delta P}
$$

ΔP 默认取 `max(1% × base_mw, 50 kW)`。

### 步长选择的依据（实测）

| ΔP | ∂V_bus17/∂P (p.u./MW) |
|---|---|
| 30 kW（1%） | 0.033880 |
| 100 kW | 0.033880 |
| 300 kW | 0.033891 |

**结果稳定到 5 位有效数字**。太小（<10 kW）会被潮流收敛容差（1e-8 MVA）的噪声淹没；
太大（>30%）二次项开始污染。测试里断言 ΔP 从 1% 变到 10% 结果变化 < 1%。

### 三个电压灵敏度，只有两个有决策意义

| 符号 | 实测值 (bus17, 3 MW) | 含义 |
|---|---|---|
| `d_vmin_dp` | **1.1e-13** | 全天最低电压/MW —— **恒为 0** |
| `d_vmax_dp` | 0.03296 | 全天最高电压/MW |
| `d_v_bus_at_peak_dp` | 0.03388 | 注入节点在光伏峰值时刻的自身电压/MW |

**`∂V_min/∂P` 恒为 0 是物理事实，不是数值误差**：全天最低电压出现在负荷高峰、
光伏出力为 0 的时刻（IEEE 33 是 20:00），那一刻的潮流与装机容量完全无关。

排期 4.3 原文要求"差分求 ∂V_min/∂P"。我们照做了，并如实返回这个 0，
同时指出决策应看后两个量。如果只交一个 0，接口看起来像坏了；如果把它藏起来，
就无法解释为什么承载力仍受电压限制——因为限制来自**上限**。

### 末端 vs 首端（排期 DoD 第 2 条）

光伏峰值时刻（13:00）的自身电压灵敏度：

| 节点 | 电气距离 | ∂V/∂P (p.u./MW) |
|---|---|---|
| bus 1 | 0.09 Ω | 0.000355 |
| bus 5 | 2.15 Ω | 0.00858 |
| bus 17 | 11.06 Ω | 0.0410 |

**末端是首端的 115 倍**，方向为正（光伏抬升电压），符合物理直觉。

### 2 节点解析对照（排期 DoD 第 5 条）

单线路 10 kV、R = 0.5 Ω、Z_base = 100 Ω（S_base = 1 MVA）：

$$\frac{\partial V_2}{\partial P} \approx R_{pu} = \frac{R}{Z_{base}} = \frac{0.5}{100} = 0.005\ \text{p.u./MW}$$

（近似成立的条件是 V₂ ≈ 1.0 p.u. 且忽略负荷电流的变化；松弛节点电压恰为 1.0。）

实测中心差分 **0.004996**，相对误差 **0.08%**。直接用潮流逐点验证
（P = 0.40/0.60 MW 两点差分）得 **0.005005**，同样吻合。

测试只断言量级（0.003–0.007）与符号，不假装精确——二阶项与负荷水平都会影响它。

## 5. 瓶颈排序（4.4）

排期要求"约束裕度消耗率必须落地成一个可排序的数值指标"。定义：

$$
\text{headroom}_e = \min_{t:\ \text{slope}_e(t) > 0} \frac{\text{margin}_e(t)}{\text{slope}_e(t)}, \qquad
\text{consumption\_rate}_e = \frac{1}{\text{headroom}_e}
$$

含义："再增加多少 MW，该设备在**它自己最紧的那个时刻**就会越限"。

### 两个必须踩对的点（都是实测踩出来的）

**1. 必须逐元素、逐时段取最小值。**
第一版用"全网最大负载率时刻"统一算，结果所有裕度都是无穷大——
因为全网最大负载率出现在**夜间负荷高峰**（20:00），那时光伏出力为 0，所有斜率都是 0。

**2. 斜率必须逐时段精确值，不能用峰值斜率 × 出力系数缩放。**
这个近似本身不差（实测偏差 1.3%–3.5%），但没必要——中心差分本来就产出了
全时段矩阵 `(96 × n_bus)`，直接用即可，没有额外成本。

### 实测排序（bus17 接 3 MW）

| rank | 设备 | 约束 | headroom | 最紧时刻 | 当前裕度 |
|---|---|---|---|---|---|
| 1 | bus 17 | voltage_high | **0.073 MW** | 13:30 | 0.0024 p.u. |
| 2 | bus 16 | voltage_high | 0.319 MW | 13:30 | 0.0098 p.u. |
| 3 | bus 15 | voltage_high | 0.827 MW | 13:30 | 0.0221 p.u. |

**headroom 0.073 MW 与 I3 二分结果 3.069 − 3.0 = 0.069 MW 吻合到 6%**。
这是 I3 与 I4 的交叉验证：线性外推与非线性搜索在同一场景下给出同一答案。
测试里断言两者相差 < 50 kW。

### 已越限时 headroom 为负

若基准容量已超过承载力，`headroom_mw < 0`（超出多少 MW），并置
`already_violated=true`、`consumption_rate=null`。排序仍然有效（负值排最前）。

## 6. 接入点对比（4.5）

给定等容量，比较 2–5 个候选节点。评分：

```
score = 1000·[可行] − 100·最大相对越限幅度 − 0.01·最大线路负载率 − 10·不收敛时段数
```

可行者恒排在不可行之前；同一组内越限越轻越靠前。输出 `recommended_bus` 与
自然语言 `rationale`。

### 与 I3 的自洽性（排期 DoD 第 3 条）

| 节点 | I3 承载力 | 5 MW 时 | 9.5 MW 时 |
|---|---|---|---|
| bus 1 | 13.95 MW | 可行 | **可行** |
| bus 8 | 7.39 MW | 可行 | 越限 2.39% |
| bus 32 | 5.03 MW | 可行（差 25 kW） | 越限 7.50% |
| bus 17 | 3.07 MW | **越限 5.49%** | 越限 16.07% |

**容量一定时，越限程度的排序严格与承载力排序相反**：13.95 > 7.39 > 5.03 > 3.07
对应越限 0% < 2.39% < 7.50% < 16.07%。这是两条独立路径（二分搜索 vs 单次仿真）
得到的一致结论。

## 7. 接口

```
GET  /api/analysis/attribution/{task_id}   归因报告 + 热力图（读已落盘的 Parquet）
POST /api/analysis/sensitivity             灵敏度 + 瓶颈排序
POST /api/analysis/compare                 2–5 个接入点对比
```

`attribution` 读的是 I2 落盘的时序结果，不重算潮流——所以"归因"与"当时判定为越限"
用的是同一份数据，天然可交叉核对。约束由 query 参数指定：

```bash
curl "localhost:8010/api/analysis/attribution/{taskId}?merge_gap=4&constraints_preset=gbt_12325"
```

```json
// POST /api/analysis/sensitivity
{"bus": 17, "base_mw": 3.0, "include_matrices": false, "top_n": 10}
```

```json
// POST /api/analysis/compare
{"buses": [1, 8, 17, 32], "capacity_mw": 5.0, "with_sensitivity": true}
```

错误码沿用全局约定：`40002` 参数错误（节点不存在、ΔP 不合法、候选点数量不对）、
`40404` 任务不存在或未成功。

## 9. 已知局限

1. **headroom 是线性外推**：不跨越约束切换，也不考虑灵敏度随容量的二阶变化。
   实测与非线性搜索吻合到 6%，但不能替代 I3 的二分结果。
2. **热力图只给越限单元**：想看"离越限还有多远"需要另外查询，或把
   `HEATMAP_CLAMP` 的正值部分也输出（当前刻意不输出）。
3. **对比的评分权重是人定的**：`1000 / 100 / 0.01 / 10` 这几个系数的量级是为了让
   "可行性 > 越限幅度 > 负载率 > 不收敛"的优先级严格成立，不是物理量。
4. **灵敏度只在单接入点下有意义**：多接入点的联合灵敏度需要偏导矩阵，属于后续迭代。
5. **不收敛时段不参与归因**：与 I2/I3 一致，单独计入 `n_unconverged`。
