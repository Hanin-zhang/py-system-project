# 承载力评估（I3）

> 本文回答一个问题：**某个节点最多能接多少光伏，是被什么卡住的。**
> 所有数字均可由 `uv run python scripts/verify_hc.py` 复现。

---

## 1. 定义

在给定算例、负荷曲线、光伏曲线、约束下，单节点最大装机容量 $C^*$：

$$
C^* = \max\{\, c \;\big|\; \forall t \in [0, 96),\ \text{所有节点与设备在时刻 } t \text{ 均满足约束且潮流收敛}\,\}
$$

**"区间内全部可行"**，而非"存在某个可行容量"。这条区别在可行性非单调时是决定性的：
若小容量不可行、大容量又可行，本平台返回**第一次变为不可行之前**的容量（保守口径）。

术语：

| 字段 | 含义 |
|---|---|
| `max_mw` | $C^*$，单位 MW |
| `limiting_type` | `voltage_high` / `voltage_low` / `line_overload` / `trafo_overload` / `not_converged` / `baseline_infeasible` / `not_reached` |
| `limiting_element_index` | 卡住的设备编号（bus / line / trafo index） |
| `limiting_time` | 该设备**首次**越限的时刻 |
| `limiting_value` | 该设备在越限时段内的**最严重**值 |
| `search_method` | `bisection`（单调）/ `linear`（非单调兜底）/ `none` |

---

## 2. 求解流程

```
1. 基线 C=0 评估 ──不可行──► max_mw=0, limiting_type=baseline_infeasible
        │可行
2. 括号倍增：0.5 → 1 → 2 → 4 … MW，直到不可行（上限 max_capacity_mw）
        │
3. 单调性粗扫（10 点）：检查可行性前缀 + max_vm 不降 + 线路最大负载率不降
        │
   ├── 单调 ──► 在"最后可行点 / 首个不可行点"之间二分（精度 10 kW）
   └── 非单调 ─► 线性扫描（上界/100 步长）→ 在首个不可行点前再二分
        │
4. 探针：C* + 50 kW 必须不可行，否则 probe.passed=false（视为 bug）
```

每一步的评估结果都留在 `curve` 里，前端可直接画"容量 → 电压/负载率"曲线。

### 为什么二分之前必须验证单调性

二分成立的前提是"可行性关于容量单调"。文献里常用这个假设，但它并不总成立：
光伏在低容量时抵消负荷、减少线路电流，线路负载率可能**先降后升**；接入点切换或
无功倒送也可能造成非单调。若不验证就二分，会得到偏大的答案——而且表面看起来完全正常。

因此本平台把单调性验证设为**强制前置步骤**，并做三件事：
1. 检查可行性是否呈"前缀"形态（这是二分真正依赖的性质）
2. 分别检查 `max_vm`、`max_line_loading` 的非降性
3. 不满足时**逐条写明原因**，退化为线性扫描并记录 `search_method=linear`

### 关于"最差电压随容量下降"

排期原文写"容量↑ → 最差电压↓"。实测**不成立**，且原因很清楚：

- 全天最低电压出现在**负荷高峰、光伏出力为 0** 的时段
- 因此 `min_vm` 与装机容量无关，实测在 0–6 MW 全程恒为同一数值（趋势 `flat`）
- 随容量单调变化的是正午的**最高电压**（过电压）

所以单调性检查针对 `max_vm`；`min_vm` 仅作为 `min_vm_trend` 记录，不参与判定。

## 3. 约束

| 预设 | 电压 | 负载率 | 说明 |
|---|---|---|---|
| `gbt_12325`（默认） | 0.93–1.07 p.u. | 100% | GB/T 12325 20 kV 及以下三相供电电压偏差 ±7% |
| `relaxed_0.90_1.10` | 0.90–1.10 p.u. | 100% | ±10%，文献中对 IEEE 33 常用；**非国标**，仅作敏感性对照 |

限值为**闭区间**：恰好等于 1.07 / 0.93 / 100% 算合规。不收敛的时段一律视为不可行，
计为 `not_converged` 违规项，不会被静默跳过（大容量下潮流发散本身就说明接不进去）。

### IEEE 33 在 GB/T 下基线即越限

这是必须先说清楚的事实：

| 场景 | 基线最低电压 | GB/T 0.93 判定 |
|---|---|---|
| IEEE 33 + 全年负荷峰值日 | 0.9131 p.u. @ 10:00 | ✗ 已越限 |
| IEEE 33 + 仿真典型日（负荷峰值系数 1.0） | 0.9131 p.u. @ 20:00 | ✗ 已越限 |
| IEEE 33 + SimBench 光伏最大日 | 0.9409 p.u. @ 20:00 | ✓ 合规 |

0.9131 p.u. 与 Baran & Wu (1989) 原始算例的已知结果一致，是**算例本身的属性**：
这条馈线在满负荷时末端电压已经跌破 ±7%。因此：

- 用满负荷日评估时，`max_mw` 会得到 **0**，`limiting_type=baseline_infeasible`
- 这不是程序错误，也不是"光伏有害"的结论，而是"该网络在评估工况下已无电压裕度，
  应先治理再谈接入"
- 接口如实返回该结果，并给出越限节点与数值，而不是把约束放宽以"算出个数"

## 4. 实测结果

算例 `ieee33_ampacity`（IEEE 33 + 载流量 0.29 kA，见 §6），
曲线 SimBench 光伏最大日（2016-05-13），约束 `gbt_12325`，96 时段：

| 节点 | 距电源电气距离 (Ω) | max_mw | 受限类型 | 受限设备 | 首次越限 |
|---|---|---|---|---|---|
| 1 | 0.09 | 13.950 | `line_overload` | line 0 | 13:00 |
| 5 | 2.15 | 12.900 | `voltage_high` | bus 5 | 13:30 |
| 8 | 4.08 | 7.394 | `voltage_high` | bus 8 | 13:30 |
| 12 | 7.16 | 4.506 | `voltage_high` | bus 12 | 13:30 |
| 17 | 11.06 | 3.069 | `voltage_high` | bus 17 | 13:30 |
| 24 | 2.83 | 8.838 | `voltage_high` | bus 24 | 13:00 |
| 30 | 5.98 | 5.500 | `voltage_high` | bus 30 | 13:30 |
| 32 | 6.64 | 5.025 | `voltage_high` | bus 32 | 13:30 |

（电气距离 = 沿在运线路累加的电阻，见 `verify_hc.py`）

主干（1→17）承载力严格递减：**13.95 > 12.90 > 7.39 > 4.51 > 3.07 MW**。

### 两种受限类型的物理解释

- **bus 1 是线路受限**：紧邻电源，电压抬升余地大（到 13.95 MW 也远未到 1.07），
  但光伏倒送要经过 line 0 回送主网。13.95 MW × 13:00 出力系数 ≈ 8.6 MW，
  扣除本地负荷后反向电流约 0.29 kA，刚好达到载流量。
- **bus 17 是电压受限**：处于电气末端（11.06 Ω），3.07 MW 就把该节点抬到 1.07 p.u.，
  此时线路负载率只有约 46%，离过载很远。这是配电网分布式光伏最典型的现象。

### 分支末端不一定比主干末端弱

bus 24（8.84 MW）> bus 12（4.51 MW），bus 32（5.03 MW）> bus 17（3.07 MW）。
原因不是"接在分支上更好"，而是这些分支的累计电阻（2.83 Ω / 6.64 Ω）小于主干末段
（7.16 Ω / 11.06 Ω）。**决定承载力的是到电源的电气距离，不是拓扑层级**。
"越靠末端承载力越低"只在同一条路径上成立。

## 5. 性能

| 操作 | 实测 |
|---|---|
| 单节点（96 时段，20–24 次全天评估） | 9.5 – 11.5 s |
| 8 节点串行 | 84.7 s |
| 5 节点串行 | 53.4 s |
| 5 节点进程池 `workers=5` | 20.8 s（2.6×，结果逐位一致） |

排期要求单节点 < 40 s、5 节点 < 3 min，串行即已满足，因此**默认 `workers=1`**：
结果顺序与日志更易追踪，也不需要为每个进程重复 import pandapower。

线程池**不可用**：实测 5 节点 26.7 s（串行）→ 30.5 s（2 线程）→ 38.5 s（8 线程），
GIL 与 pandas/numpy 的争用让并行变成负收益。因此接口只暴露进程数。

优化手段（按收益排序）：
1. **复用一张网**：`TimeseriesRunner` 只构建一次 pandapower 网络，之后仅改 `sgen.p_mw` 列
2. **热启动**：第 2 个时段起 `init="results"`，实测与冷启动逐点差 5.5e-10 p.u.
3. **评估缓存**：粗扫 / 二分 / 探针可能评估同一容量，按容量去重

## 6. 数据来源与假设

| 数据 | 来源 | 性质 |
|---|---|---|
| 网络参数 | `pandapower.networks.case33bw()`（Baran & Wu 1989） | 公开标准算例 |
| 负荷 / 光伏曲线 | SimBench 1.5.3，`1-MV-rural--0-sw`，2016 年 | 公开标准数据集，**非模拟** |
| 线路载流量 | pandapower 标准线型 `70-AL1/11-ST1A 10.0`，0.29 kA | 选型假设 |

### 曲线导出

`scripts/import_simbench_profiles.py` 导出两个设计日，并逐点复核了 SimBench 曲线确实是
"相对元件额定值的 p.u. 乘子"：

- **光伏最大日** 2016-05-13：PV3 日发电量全年最高（等效 4.21 h），负荷系数 0.23–0.70。
  承载力评估默认用这一天——它是过电压最不利的工况。
- **负荷峰值日** 2016-01-22：馈线总负荷达到全年峰值（系数 1.0），用来看低电压问题。
- 排除 3/27、10/30（夏令时切换，不是 96 点）

归一化口径（唯一的"人为选择"，写进 `simbench_manifest.json`）：
- 负荷 = 该馈线全部负荷逐时段求和 ÷ 全年峰值
- 光伏 = PV3 原始 p.u.，**不二次归一化到 1.0**（真实光伏极少满载，硬拉到 1.0 会系统性低估承载力）
- SimBench 时间戳为当地时间；5/13 处于 CEST，正午峰值出现在 13:00 左右属正常

### 载流量假设

原算例 `max_i_ka=99999`，线路负载率恒为 0，I3 的"线路受限"永远无法触发。派生算例
`ieee33_ampacity.json` 把全部线路改为 0.29 kA（pandapower 内置标准线型，
由 `export_cases.py` 直接从 `pp.load_std_type()` 读取，非手工填值）：

- 基线最大电流 0.210 kA → 负载率 72.5%，既不过载，也留出了倒送触发过载的空间
- **只改这一项**，阻抗仍为原算例参数（未换成该线型的阻抗）
- `ieee33.json` 保持原样，未做任何修改

## 7. 接口

```
POST /api/hc/single          单节点
POST /api/hc/batch           多节点（各节点独立）
GET  /api/hc/{task_id}       结果摘要（落库行）
GET  /api/hc/{task_id}/curve 指定节点的扫描曲线
GET  /api/hc/presets         约束预设
```

请求示例：

```json
{
  "case_ref": "ieee33_ampacity",
  "bus": 17,
  "constraints": {"preset": "gbt_12325"},
  "options": {"tol_mw": 0.01, "max_capacity_mw": 50},
  "load_profile_path": "calc/data/profiles/simbench_pv_max_day_20160513_load.csv",
  "pv_profile_path": "calc/data/profiles/simbench_pv_max_day_20160513_pv.csv"
}
```

错误码：

| code | 含义 |
|---|---|
| 40002 | 参数错误（节点不存在、曲线非法、约束预设未知、`tol_mw` 不细于探针偏移） |
| 40404 | 任务或节点结果不存在 |
| 0 | 成功（**注意**：`max_mw=0` 且 `limiting_type=baseline_infeasible` 也是成功） |

## 8. 已知局限

1. **单节点独立评估**：批量接口中各节点互不叠加，不是"多个接入点同时接入"的联合承载力
2. **功率因数固定**：目前只支持恒功率因数（默认 1.0，不吞吐无功）；逆变器无功控制属于 I5
3. **容量按比例缩放**：所有时段的出力 = 装机容量 × 曲线系数，不考虑逆变器限幅
4. **任务表为进程内 + SQLite**：重启后 API 侧任务记录丢失（结果仍在 SQLite 与明细 JSON 中）
5. **不收敛即不可行**：大容量下潮流发散直接判为不可行，不做电压稳定极限的进一步分析
